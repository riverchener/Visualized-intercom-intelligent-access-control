# 视频监控子系统（RK3506B 智能社区）

> 在原有"智慧社区"Qt 应用之外**新增**的一个独立子系统：**设备端采集编码推流 + 流媒体中转 + Web 实时预览**。
> 原有社区业务代码**零改动**（边界见下文）。
>
> 📚 **配套文档**：
> - 教程 **第 11 章**（`docs/02_开发教程_从0到1.md`）= "从零写出这套系统"的完整实战；
> - **Q43~Q51**（`docs/03_开发难点与常见问题.md` 第九章）= 本子系统实际踩到的坑；
> - 接线（摄像头/麦克风/摄像头独占提醒）= `docs/01_接线指南.md` 2.5 节；
> - 本目录 `docs/设计与实现.md` = 协议、部署、运维、限制的详细设计。

## 1. 角色与边界

| 角色 | 跑在哪 | 职责 | 明确不做 |
|---|---|---|---|
| **RK3506B 设备端** | 开发板 | 音视频采集 → 编码压缩 → 网络推流；设备插拔监控；网络断线自动重连；接收后台指令；上报在线状态/心跳 | ❌ 不做解码 ❌ 不做录像存储 |
| **流媒体中转服务** | Ubuntu 虚拟机（也可放任意能被设备访问的机器） | 接收设备推流；**多客户端同时拉同一路流**；**录像落盘**；设备状态跟踪；给后台/Web 提供 API | ❌ 不做转码（原样转发已压缩帧） |
| **Web 浏览器客户端** | 宿主机浏览器 | 实时预览播放；**解码在浏览器侧**（MJPEG 原生解码 + JS 解码 A-law 音频）；启停/录像/截图操作 | ❌ 不参与采集 |
| 智能社区业务后台 | （本子系统提供 API 供其调用） | 通过 API 控制推流启停、查询设备状态 | — |

**与原有社区业务的交互边界（重要）**：
- 设备端是**独立进程** `av_stream`，与 Qt 应用 `intelligent_community` 互不依赖、可单独启停；
- 文件/端口/设备节点全部分开：`av_stream` 用 `/dev/video0`、TCP 9100，Qt 应用用 `/userdata/smart_community/*` 与 weston；
- **不改动任何原有业务源码**（本次未修改任何社区业务逻辑文件，只新增 `video_surveillance/` 目录）；
- 若将来要在 Qt 界面上加"监控"入口，只需新开进程/显示浏览器页面，不用动原有页面逻辑。

> ⚠️ **唯一会互相影响的地方：摄像头是独占资源。**
> 原有 Qt 应用的"视频监控"页也用 V4L2 直接打开 `/dev/video0`，而且**离开页面后不释放**
> （原工程遗留的 fd 泄漏）。UVC 摄像头同一时刻只能被一个进程流式占用，所以：
>
> | 场景 | 结果 |
> |---|---|
> | 只跑推流（不点老界面那个"视频监控"页） | ✅ 推流正常 |
> | 先在 Qt 里点开过"视频监控"页 | ❌ 推流打不开摄像头：日志 `设置像素格式失败（Device or resource busy）` |
> | 释放办法（不需要改代码） | `adb shell "/etc/init.d/S99smart_community restart"` |
>
> 按"不改动原有业务逻辑"的约束，本项目**没有**去改那个老页面，
> 而是让 `av_stream` 把原因直接打进日志（含释放命令），并在本文档记录。
> 生产建议：老页面的本地预览与新推流二选一，或在业务侧把摄像头统一交给 `av_stream`。

## 2. 系统架构

```
┌──────────────────── RK3506B 设备端 (av_stream) ────────────────────┐
│                                                                    │
│  USB 摄像头 ──V4L2──► video_thread ─┐                              │
│   (MJPG 640x480~1920x1080)          │ 视频帧队列(满则丢最旧,低延迟) │
│                                     ├──► pusher_thread ──TCP 9100──┼──►
│  麦克风/声卡 ──ALSA──► audio_thread ─┘   · 帧封装(SCAV TLV)        │
│   (16bit PCM→G.711 A-law 8k)            · 心跳/状态(1s)            │
│                                          · 接收 start/stop 指令     │
│  health_thread: 摄像头/声卡插拔检测 + 网络断线指数退避重连          │
└────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────── 流媒体中转服务 (stream_server.py, asyncio) ────────────────┐
│  TCP 9100  接收设备推流 ──► 每路设备: 最新帧 + 音频环形缓冲 + 状态/事件      │
│  HTTP 8080                                                                 │
│    /                    监控页面(Web 客户端)                                │
│    /live/<dev>.mjpg     实时视频 → 每个客户端一个队列，共享同一帧源(扇出)   │
│    /live/<dev>.alaw     实时音频(G.711 A-law)                              │
│    /snapshot/<dev>.jpg  抓一张当前画面                                     │
│    /api/devices         设备在线/帧率/码率/录像状态(业务后台用)             │
│    /api/stream/<dev>?action=start|stop   下发指令给设备                     │
│    /api/record/<dev>?action=start|stop   服务侧录像开关                     │
│    /api/recordings/<dev>                  录像文件列表                      │
│    /recordings/<dev>/<file>               录像下载                          │
│  recorder: 把设备 JPEG 帧按段写 .mjpg(32MB 切段) —— 录像在服务侧           │
└───────────────────────────────────────────────────────────────────────────┘
                                  │ HTTP 8080
                                  ▼
                    Web 浏览器（MJPEG <img> + Web Audio 解码 A-law）
```

## 4. 快速开始（4 步）

### 步骤 1：编设备端（Ubuntu 虚拟机）

```bash
bash video_surveillance/scripts/build_device.sh
# 产物: ~/video_surveillance/build/av_stream (ARM 32bit, 32KB)
```

### 步骤 2：起流媒体中转服务（虚拟机）

```bash
bash video_surveillance/scripts/run_server_vm.sh          # 后台常驻
bash video_surveillance/scripts/run_server_vm.sh status   # 看状态
bash video_surveillance/scripts/run_server_vm.sh stop     # 停止
```

### 步骤 3：设备端推流（开发板）—— **装成开机自启（推荐）**

```bash
bash video_surveillance/scripts/install_av_on_board.sh
# 它会：推送 av_stream → 安装 /etc/init.d/S98av_stream → 写 /etc/default/av_stream → 立刻启动
```

手动方式：

```bash
adb push ~/video_surveillance/build/av_stream /userdata/av_stream
adb shell "chmod 755 /userdata/av_stream"

# 开机自启（推荐）：板子重启后自动上线
adb shell "/etc/init.d/S98av_stream start|stop|restart|status"

# 或临时手动跑（重启后失效）
adb shell "SERVER=192.168.137.94:9100 sh /userdata/av_stream_start.sh --real"
adb shell "SERVER=192.168.137.94:9100 sh /userdata/av_stream_start.sh"   # 无摄像头用测试图案
```

改中转服务地址/分辨率：编辑板子的 `/etc/default/av_stream`：

```ini
SERVER=192.168.137.94:9100
DEVICE_ID=rk3506b-01
SIZE=1920x1080      # 画质最好；带宽/存储紧张就改 1280x720
FPS=15              # 15 够用；要更顺滑改 30（码率翻倍）
# CTRL=sharpness=3,contrast=10
# AUDIO=hw:0,0      # 有麦克风时打开
```

改完 `/etc/init.d/S98av_stream restart` 生效。

### 帧率/画质能调到多少（实测）

| 配置 | 实测 fps | 码率 | 单帧 | 板端 CPU | 1 小时录像 |
|---|---|---|---|---|---|
| 640×480 @30 | 30.0 | 10.5 Mbps | 45 KB | 2.0% | 4.6 GB |
| 1280×720 @15 | 15.0 | 14.0 Mbps | 120 KB | 1.8% | 6.2 GB |
| 1280×720 @30 | 30.1 | 27.9 Mbps | 119 KB | 3.2% | 12.3 GB |
| **1920×1080 @15（默认）** | **15.0** | **27.6 Mbps** | **236 KB** | **2.6%** | 12.2 GB |
| 1920×1080 @30 | 30.1 | 53.7 Mbps | 229 KB | 4.0% | 23.6 GB |

- **帧率上限是摄像头的 30fps**（板子 CPU 只用 2~4%，完全不是瓶颈）；
- **画质上限由摄像头固件决定**：UVC 不暴露"JPEG 压缩质量"控制项，
  所以提高画质靠**提高分辨率**（1080p 单帧 236KB vs 720p 120KB）；
- 想自己控制 JPEG 质量只能改用 YUYV + 本程序软编，但 YUYV 下 1080p 只有 5fps，
  **帧率损失太大，不推荐**；
- 观感类参数（锐度/对比度/饱和度/伽马/亮度）可以用 `--set-ctrl` 调。

### 步骤 4：浏览器看画面

在宿主机浏览器打开：**`http://192.168.137.94:8080/`**
（页面里可以开始/停止监控、开始/停止服务端录像、截图、开声音）

## 5. 实测结果（RK3506B + 1bcf:2281 USB 摄像头）

| 验证项 | 结果 | 证据 |
|---|---|---|
| 摄像头识别 | ✅ | `1bcf:2281 "2M"` UVC；`/dev/video0`；支持 **MJPG 640×480~1920×1080@30fps** |
| 编码方式 | ✅ | 摄像头**直出 MJPEG**（板子零编码开销）；不支持时自动退化 YUYV+libturbojpeg 软编 |
| 设备→服务推流 | ✅ | `[tcp] 设备注册: rk3506b-01 (192.168.137.85:xxx)`；1280×720 实测 ~10fps、≈800KB/s |
| 多客户端同时拉流 | ✅ | 3 个并发客户端各拿到 **62 帧/6 秒**（与设备端帧率一致，真扇出） |
| 抓图 | ✅ | `/snapshot/rk3506b-01.jpg` 90KB 有效 JPEG（**真实画面**，见下） |
| 服务端录像 | ✅ | `recordings/rk3506b-01/*.mjpg` 持续增长，内含 888 帧有效 JPEG（历史实测；2026-10-20 已删除录像功能） |
| 后台指令启停 | ✅ | `stop` 后 4 秒内新增 0 帧；`start` 后恢复（4 秒内 +40 帧） |
| **网络断线自动恢复** | ✅ | 重启中转服务后，设备**2 秒内自动重连**并继续推流/录像 |
| 音频链路（A-law） | ✅ | 板载 ES8388 采集 8kHz mono → A-law 20ms/包 → 服务端 711KB → 客户端 3 秒拉到 28KB |
| 设备插拔事件上报 | ✅ | 设备端上报 `camera_plugged`；服务端 `[event]` 记录（拔插检测逻辑同路径） |
| **摄像头物理拔插 + 自动恢复** | ✅ | 拔下 → `camera_unplugged`(14:19:47) → 每秒重试打开 → 插回 → `camera_plugged`(14:20:03) → **自动恢复推流，进程全程未重启** |
| 心跳与在线状态 | ✅ | 每秒心跳；服务端 6 秒无心跳标记 `offline` |

## 7. 网络拓扑要求（**部署前必读**）

本环境实测结论：

| 方向 | 是否通 | 说明 |
|---|---|---|
| 设备(eth0 192.168.137.85) → 虚拟机(ens37 192.168.137.94) | ✅ 通（1.6ms） | 板子 eth0 与虚拟机 ens37 同网段，中转服务能收到推流 |
| 宿主机浏览器 → 虚拟机 8080 | ✅ 通 | 宿主机在 192.168.137.1（同一网段），或走 192.168.88.130 |
| 设备 → 宿主机（当服务在宿主机上跑时） | ✅ 通 | 同一 WiFi 网段 10.17.102.x |
| 设备 → 虚拟机 ens33（NAT 网段 192.168.88.x） | ❌ 不通 | NAT 入向被挡；所以**服务要放在设备能直连的网段** |

**部署要点**：中转服务必须放在"设备能主动连到、浏览器也能访问"的机器上。
两种可用形态：
1. **服务在虚拟机**（本环境采用）：板子 eth0 ↔ VM ens37 同网段；
2. **服务在宿主机/服务器**：设备推流到该机 IP:9100，浏览器访问该机 8080。
